  ## The problem

  Renfe publishes open real-time data (GTFS-Realtime) for its commuter rail network: where each train is, how late it is and which official alerts are active, updated every few seconds. Hundreds of trains across many lines produce a constant stream of updates, so no person can follow everything at once.

  RailOps tries to answer one practical question: **which line should an operator look at first, and why?**

  ## What RailOps does

  1. **Collects** Renfe's real-time feeds every 30 seconds and stores them in a local SQLite database, together with Renfe's static GTFS timetable.
  2. **Shows** the current position and published delay of every train on a map.
  3. **Compares** the last minutes with the previous minutes, line by line, to detect what is getting worse.
  4. **Estimates** (experimentally) which trains that are currently on time may exceed 5 minutes of delay in the next 10 minutes.
  5. **Explains** the situation of a line in plain language with IBM Granite, running locally, and checks the generated text before showing it.

  The dashboards only read the database (`mode=ro`); the collector is the only process that writes to it.

  ## Applications

  ### 1. Main dashboard: `app.py` (port 8501)

  - Map of trains (Folium, dark-styled tiles), coloured by published delay:
    - green: less than 3 min
    - orange: 3 to 10 min
    - red: 10 min or more, or cancelled
    - grey: data older than 120 s, or no delay published
  - Table of lines with observed trips, trips delayed 5 min or more, cancellations, mean and maximum delay.
  - Report for a selected line generated by **IBM Granite** (3 sentences, in English). Every number in the text is checked against the input data by `validar_granite.py`; if Granite invents a number or is not available, a fallback template is shown instead.

  ### 2. Analytics dashboard: `app_analitica.py` (port 8502)

  A separate Streamlit application with three tabs. It does not modify `app.py` or the database.

  - **Evolución (Evolution):** compares the last window (10, 15, 20 or 30 min) with the previous one for every line of the selected network. Each trip counts once per window (its last observation). Lines are classified with explicit rules (high priority, medium priority, sustained high level, improving, stable, not enough data). Includes a time-series chart and a replay mode to choose any past moment.
  - **Predicción experimental (Experimental prediction):** a small gradient-boosting model written in pure Python estimates, for trips currently under 5 min of delay, the risk of reaching 5 min or more 10 minutes later. It is trained on an earlier period and evaluated on a later one, and the tab shows its metrics against a simple baseline (the current delay), a calibration chart and feature importance.
  - **Evidencias y explicación (Evidence and explanation):** evidence for one line (figures, trips present in both windows, official alerts, model risk, data limitations) and a short explanation written by IBM Granite. Granite receives short factual sentences, and its answer is rejected if it is JSON, misses the line or the current percentage, describes the wrong direction of change, contradicts the alerts or uses numbers that are not in the data. In that case a verifiable template is shown.

  The analytics code uses only the Python standard library (no numpy, pandas, pyarrow or scikit-learn). Charts and tables are drawn with HTML/SVG instead of Arrow-based Streamlit components.

  ### 3. Environment check: `diagnostico_railops.py`

  A Streamlit page that checks the Python environment, installed packages and read-only access to the database, without running the collector or Granite.

  ## Architecture

  ```text
          [ Renfe GTFS-Realtime (JSON) + GTFS static timetable (ZIP) ]
                                    │  every 30 s
                                    ▼
                    [ enlace_recolector.py ]  (only writer)
                                    │
              ┌────────────────────┴─────────────────────┐
              ▼                                          ▼
    [ enlace_datos/enlace.db ]              [ enlace_datos/salida/ ]
          (SQLite)                         estado_actual.json
              │  read-only                 estaciones.geojson
      ┌───────┴──────────┐                       │
      ▼                  ▼                       ▼
  railops_logica.py   railops_analitica.py   railops_mapa.py
      │                  │                       │
      ▼                  ▼                       │
    app.py ◄──────────────┼───────────────────────┘
    (8501)                ▼
      │           app_analitica.py (8502)
      │                  │
      └────────┬─────────┘
                ▼
    railops_granite.py  →  IBM Granite (llama-cpp-python, local)
    validar_granite.py  →  number check + fallback template
  ```

  ## Repository structure

  ```text
  ├── app.py                   # Main Streamlit dashboard (map, line table, Granite report)
  ├── app_analitica.py         # Analytics dashboard: Evolution, Prediction, Evidence tabs
  ├── railops_logica.py        # SQL queries and metrics used by app.py
  ├── railops_analitica.py     # Window comparison, time series, pure-Python model, metrics
  ├── railops_mapa.py          # Folium map and train colours
  ├── railops_granite.py       # IBM Granite loader and report generation
  ├── validar_granite.py       # Numeric validator and fallback template
  ├── enlace_recolector.py     # Continuous collector: GTFS static + GTFS-RT into SQLite
  ├── recopilar_renfe.py       # Earlier standalone collector (not used by the dashboards)
  ├── diagnostico_railops.py   # Environment and database check (Streamlit)
  ├── requirements.txt         # Python dependencies
  └── README.md
  ```

  Not included in the repository (see `.gitignore`): the `enlace_datos/` folder with the database, the trained model folder `modelos/` and the Granite `.gguf` file.

  ## Installation and running on LinuxONE

  ### 1. Clone and install

  ```bash
  git clone https://github.com/sjvelloz/renfe_datathon
  cd renfe_datathon
  pip install --user -r requirements.txt
  ```

  `requirements.txt` contains what the dashboards need (Streamlit, Folium and streamlit-folium). The collector only needs the Python standard library. Optional packages:

  ```bash
  pip install --user llama-cpp-python        # IBM Granite (otherwise the fallback template is used)
  pip install --user gtfs-realtime-bindings  # lets the collector compare the .pb feeds with the JSON ones
  pip install --user requests                # only for the earlier collector recopilar_renfe.py
  ```

  ### 2. IBM Granite model

  `railops_granite.py` loads the model from the path in the `MODELO` constant:

  ```text
  /home/linux1/renfe_datathon/granite-4-350m-be-f16.gguf
  ```

  Place the `.gguf` file there or change `MODELO`. On IBM Z (big-endian) the GGUF file must be a big-endian build. Without the model, both dashboards keep working and show the fallback template.

  ### 3. Start the collector

  ```bash
  nohup python3 enlace_recolector.py --datos ./enlace_datos > recolector.out 2>&1 &
  tail -f enlace_datos/recolector.log
  ```

  Useful options: `--intervalo` (seconds between cycles, minimum 15, default 30), `--horas` (total duration, 0 = no limit), `--sin-raw` (do not keep the original JSON files). Stop it cleanly with `kill -TERM <pid>`.

  ### 4. Start the dashboards

  ```bash
  streamlit run app.py --server.port 8501 --server.headless true
  streamlit run app_analitica.py --server.port 8502 --server.headless true
  ```

  ### 5. Open them from your computer (SSH tunnel)

  ```bash
  ssh -L 8501:localhost:8501 -L 8502:localhost:8502 user@your_linuxone_host
  ```

  Then open `http://localhost:8501` and `http://localhost:8502`.

  ### 6. Train the prediction model

  The model is not trained automatically. Train it from the "Predicción experimental" tab (button) or from the terminal:

  ```bash
  python3 railops_analitica.py --entrenar            # last 24 h of data
  python3 railops_analitica.py --entrenar --horas 48 # more history
  ```

  It is saved to `modelos/railops_riesgo.json`.

  ## Database checks

  ```bash
  sqlite3 "file:enlace_datos/enlace.db?mode=ro" \
  "SELECT feed, COUNT(*) AS captures, SUM(error IS NOT NULL) AS errors, ROUND(AVG(latencia_ms)) AS avg_latency_ms FROM capturas GROUP BY feed;"
  ```

  The collector also writes a coverage report to `enlace_datos/salida/informe_cobertura.md`.

  ## Data limitations and responsible use

  1. **Delays are published, not measured.** All figures come from Renfe's GTFS-Realtime feeds.
  2. **No infrastructure data.** RailOps does not know about switches, signals, tracks or platforms, because they are not published in these feeds.
  3. **No invented causes.** Granite is instructed not to invent causes, and the fallback templates state that a cause cannot be attributed when there is no supporting data.
  4. **Deterioration is not prediction.** The Evolution tab shows observed changes with explicit rules. The prediction tab is experimental and shows how it compares with a simple baseline.
  5. **Different trains in each window.** The analytics dashboard shows how many trips appear in both windows, because a change can come from comparing different trains.
